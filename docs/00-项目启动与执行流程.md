# 项目启动与执行流程

> 选题：**街边水果店临期果品动态定价与到店客流适配推送系统**（原清单第 9 项）
> 课程产物：**能运行的系统 + 可复现的评测报告**
> 本文档回答一个问题：**这个项目从哪里开始、按什么顺序推进、每一步怎么算做完。**
> 编写：Lead　最近更新：阶段 0 结束时

---

## 0. 项目启动流程（一页速览）

```
阶段0 选题确认与环境勘察 ──► 阶段1 数据就绪 ──► 阶段2 定价可评测 ──► 阶段3 后端闭环 ──► 阶段4 前端工作台 ──► 阶段5 演示与答辩
   决策已定稿                 硬门槛G1            硬门槛G2              硬门槛G3             硬门槛G4              硬门槛G5
   环境已跑通                 数据事实卡          评测协议+基线         链路可演示           店主能操作            对照组结果说话
```

**顺序不能调换的三条理由**

1. **评测协议必须先于定价算法。** 本项目的主线不是"我会算折扣"，而是"我的折扣比固定价/规则价损耗更低、毛利更高"。如果先把定价模块写成一个算法，再回头想怎么比，很容易变成自己造数据自己打分（自证），答辩第一个问题就会问到这个。
2. **数据必须先于一切代码。** 定价模块要吃的是"某天某单品的实际销量/售价/客流时段"，而这套东西门店不会给。所以阶段 1 的交付物不是"数据"，而是"**一份写清楚假设、能被别人复现的仿真数据 + 公开真实数据的校准依据**"。
3. **链路必须先跑通再加功能。** 入库→临期→定价→确认→推送→回流是一条链，任何一环没有接口，后面的功能都要返工。先用假数据把链路打通，再逐环替换成真实现。

## 1. 为什么是这个选题

### 1.1 三件事，一条链

| 子问题 | 系统里对应的能力 | 在报告/答辩里的分量 |
| --- | --- | --- |
| 临期识别 | 按批次记录到货日与保质期，算剩余可售天数，生成临期清单 | 基础，必须做对 |
| **动态定价** | 按剩余天数/库存/历史销量给折扣建议，并给出理由 | **核心与亮点** |
| 客流适配推送 | 用历史成交时段找高峰，给合适的人推合适的文案 | 做薄，一段链路 + 一次对比 |

**精力分配建议：定价 60%，临期台账 25%，推送 15%。** 两个核心都做深是做不完的。

### 1.2 选题代价（要主动认下来）

- 业务场景不熟悉：需求调研要多花时间，必须真去问水果店店主（哪怕只问 2 个人、20 分钟）。
- 说服力完全依赖评测设计：只展示"系统能给出折扣"是撑不住答辩的。
- 批次录入负担重：真实店主不会逐箱登记，设计上简化成按品类 + 到货日，报告里作为局限性写明。

## 2. 技术选型与理由

| 层 | 选型 | 版本 | 理由 |
| --- | --- | --- | --- |
| 后端 | Spring Boot | 3.5.0 | 课程要求的主流栈；3.5.x 是当前稳定线，Java 21 验证通过 |
| 持久层 | MyBatis-Plus | 3.5.7 | 中文资料多；**3.5.7 是最后一个同时支持 Spring Boot 3 与 H2 的版本**（3.5.9+ 移除 H2 支持） |
| 数据库 | H2（内存/文件，MySQL 兼容模式） | 2.3.232 | 零安装、可随演示启动；正式库按 MySQL 8 写 DDL，不改代码 |
| 前端 | Vue 3 + Vite + Element Plus | 收尾时锁定 | 店员/店长工作台，表格与表单为主 |
| 定价算法 | Python（numpy/pandas/scipy） | 3.14 / pandas 3.0.3 | 与数据分析、评测脚本共用一套代码，避免"Java 里再写一遍回归" |
| 文档/图表 | Python (matplotlib) + Markdown | — | 评测图表直接从脚本生成，可重跑 |

**关于"定价模块要不要单独做成 Python 微服务"**

- 开发期：定价与评测都在 Python 侧以**离线脚本 + JSON 契约**方式跑，产出 `data/seed/pricing_suggestions.json`，后端只负责读取与展示。理由：避免为课程项目引入"两个进程 + HTTP 调用"的调试成本，而算法迭代主要发生在 Python 侧。
- 收尾期：如果时间富余，再把 Python 包装成 `python-pricing-service`（FastAPI，`POST /price/suggest`），后端改为调用它，作为"架构演进"的加分项写进文档。
- **先不做微服务，是刻意的取舍，不是偷懒**——这句话要写进报告。

**环境事实（已实测）**

| 项 | 本机状态 | 处理方式 |
| --- | --- | --- |
| JDK 21 | 作者机器用 Android Studio 自带的 OpenJDK 21.0.8 | `scripts/setup.ps1` 自动探测并写入 `.tools.json` |
| Maven | **不在 PATH**，`~/.m2/wrapper/dists` 有 3.9.6/3.9.12/3.10.0 | `scripts/mvn.ps1` 统一入口；wrapper 已就位 |
| Maven 中央仓 | 直连不通，`repo1.maven.org`/aliyun/腾讯/华为镜像可达 | setup 自动探测，生成 `.mvn/settings-local.xml` |
| Node | v24.14.1 | 前端可用 |
| Python | 3.14.3（作者机器），依赖按 `requirements.txt` 安装 | 数据与评测脚本统一用装好依赖的解释器（文档里写作 `python`） |
| Docker / MySQL / Redis | 无 | 演示用 H2，不引入外部服务 |

> 环境一句话总结：**这台机器能完整跑通"Python 数据分析 + Spring Boot 后端 + Vue 前端"，前提是所有构建都走 `scripts/mvn.ps1`。**

## 3. 数据策略（本项目的关键前置）

数据拿不到是原清单里"不建议选 9"的唯一理由，所以这一段是项目的生死线。三条路同时用：

### 3.1 公开真实数据（已落地，可复现）

2023 年全国大学生数学建模竞赛 C 题（蔬菜类商品的自动定价与补货决策）附件，已下载到 `data/raw/`：

| 文件 | 内容 | 实测规模 |
| --- | --- | --- |
| `attachment1_product_info.xlsx` | 商品信息：条码、名称、分类编码/名称、损耗率% | 251 单品 / 6 大类 |
| `attachment2_sales_detail.xlsx` | 销售流水明细：日期、时刻、条码、销量(kg)、单价、销售/退货、是否打折 | **878,503 行**，2020-07-01 ~ 2023-06-30 |
| `attachment3_wholesale_price.xlsx` | 批发价：日期、条码、批发价(元/kg) | 55,982 行，覆盖 251 单品 |
| `attachment4_loss_rate.xlsx` | 损耗率：品类平均（6 类，6.68%~15.51%）+ 单品 | 251 单品 |

**结构与水果的差异（报告里要写清楚）**：蔬菜是散称（kg）、按日批发、当天基本出清；水果是标品（个/斤）、保质期以天计、允许隔夜。差异用参数吸收，不用假装一样：

| 维度 | 蔬菜（公开数据） | 水果（本项目） | 迁移方式 |
| --- | --- | --- | --- |
| 计量单位 | kg | 个 / 盒 / 斤 | 统一折算成"份"，价格用元/份 |
| 保质期 | 当天为主 | 2~10 天 | 引入`可售天数`，用公开数据的**日销量+价格弹性+损耗率**做校准，不直接搬 |
| 定价频率 | 日 | 日（可加时段） | 一致 |
| 损耗口径 | 按类平均损耗率 | 按单品损耗率 | 直接沿用"损耗率"概念，数值按水果品类调整 |

### 3.2 公开数据怎么用（三条，都要落到脚本）

1. **销量—价格关系**：用单品日销量与当日售价（含打折标记）拟合价格弹性，作为仿真器需求曲线的**取值范围依据**。
2. **时段分布**：把 878,503 条流水的时刻聚合成小时分布，得到**真实的到店客流时段形状**——这正是"客流适配推送"所需要的输入，比编造的"早中晚三峰"有说服力。
3. **损耗率与批发价波动**：作为仿真器成本与损耗参数的上界/下界。

### 3.3 仿真器（评测的主战场）

- 自己做一台**日粒度 + 时段粒度的门店销售模拟器**，输入：单品成本、保质期、需求曲线（基准需求、价格弹性、时段分布、周内效应）、消费者价格敏感度；输出：每日每单品的需求、成交、报废。
- 仿真器的价值有两个：**提供闭环数据**，以及**当评测台**——固定价格 / 规则折扣 / 模型定价三种策略跑在同一批种子、同一批消费者上，这是唯一能证明"谁更好"的方式。
- 假设必须写成清单（`docs/02-仿真器假设与数据字典.md`），并能一键重跑（固定随机种子）。

### 3.4 真实店铺（加分项，不作为前提）

找校门口水果店导出收银流水，或手工记录 2~3 周。有则做一次"仿真 vs 真实"的对照小节，没有不影响主线。

## 4. 评测协议（阶段 1 必须冻结）

**目标**：用同一份数据、同一个种子，让三种策略在同一批消费者身上跑，比较**损耗率**与**毛利**。

| 策略 | 说明 | 角色 |
| --- | --- | --- |
| 固定价格 | 按成本加成定价，不打折 | 基线 1（现状） |
| 规则折扣 | 按剩余保质期比例 + 库存分档打折 | 基线 2（店主经验） |
| 模型定价 | 估计"价格×时段→销量"，在候选折扣中选期望收益最大 | 本项目方案 |

**操作口径**

- 时间切分：公开数据用于**参数校准**；仿真器生成 **90 天营业期**，前 60 天作为策略的滚动历史窗口，**后 30 天为统一测试期**。
- 指标：`毛利额`、`损耗率=报废量/进货量`、`缺货率`、`客单价`、`折扣深度分布`。
- 每个配置跑 **≥20 个随机种子**，报告均值与标准差；不要只贴一次运行的结果。
- 结论表述：**"在 XX 假设下，模型定价相对固定价格把损耗率从 a% 降到 b%，毛利提升 c%"**，并附假设边界。

> 这份协议的每一条都会变成 `scripts/` 下的评测脚本 + `release/evaluation-report.md` 里的图表；答辩时的第一张图就来自这里。

## 6. 风险清单与预案

| 风险 | 触发信号 | 预案 | 报告里怎么讲 |
| --- | --- | --- | --- |
| 数据说服力不足 | 只有仿真数据 | 用公开数据做参数校准 + 时段分布，附校准图 | 明写"仿真 + 真实数据校准"，不假装是真实门店数据 |
| 批次录入负担重 | 店主访谈反馈"不会登记" | 简化为按品类+到货日记录 | 作为局限性写明，并给出"扫码枪/批量导入"的后续设想 |
| 定价算法过重 | 开始考虑强化学习 | 回到"回归 + 候选折扣枚举" | 说明数据量不足以支撑 RL，简单模型可解释性更强 |
| 推送模块太薄 | 只有一条"群发"按钮 | 加"选人规则（买过该品类/限频）+ 文案生成 + 打开率" | 明确定位：推送只做链路演示，核心在定价 |
| 评测自证 | 结论只在仿真器里成立 | 加公开数据上的校准验证 + 敏感性分析 | 主动写出"结论依赖的假设" |
| **证据来源混淆** | 把仿真参数当成现实依据写进需求分析 | 全项目统一"证据三类"标注（见下） | 答辩时能逐条说明每个结论的来源等级 |
| 范围蔓延 | 开始做会员积分、库存盘点等 | 用本文档第 1.1 节排序，砍掉与定价无关的功能 | 作为"后续工作" |

### 6.1 证据分级制度（全项目统一，2026-10-10 由需求分析侧提出并采纳）

写任何"事实性结论"时必须标注来源等级，禁止把仿真结果当成现实依据：

| 等级 | 标记 | 含义 | 能支撑什么 |
| --- | --- | --- | --- |
| A | **真实数据** | 公开真实流水/批发价/损耗率（878,503 条，`data/interim/`，脚本可重跑） | 形状、量级、价格—销量关系；**跨业态迁移仍需访谈确认** |
| B | **仿真设定** | 仿真器参数与输出（`data/seed/`） | 只证明"系统内部一致""策略在给定假设下更优"，**不构成对现实的佐证** |
| C | **待访谈验证** | 只有真实店主/顾客能回答 | 现状流程、价格牌做法、微信群规则、处置卖不完货物的方式 |
| — | **自设参数 / 合规原则** | 产品取舍（候选折扣档、推送上限、静默时段、数据最小化），既非实测也非仿真 | 说明"这是设计决定，不是证据推导结果"，答辩时如实表述 |

**应用要点**

- `docs/04` 第 3 节 As-Is 四张表按 A/B/C 三分类逐行标注，并写出字段级追溯路径（如 `hourly_traffic.json → overall.peak_hour`）。
- `docs/02`（仿真器）所有参数表必须标 A/B/C，B 类参数要给出"取值依据或纯假设"。
- `release/evaluation-report.md` 的结论段必须写明"本结论为 B 类证据（仿真），A 类数据仅用于参数校准"。
- 这条制度本身就是答辩材料：它证明团队清楚"自己造数据自己打分"的边界在哪。
