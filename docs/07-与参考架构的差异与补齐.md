## 0. 总体结论

参考架构的主线（批次库存 → 临期扫描 → 定价确认 → 推送 → 回流）与本系统一致，开发顺序（4 阶段）一致。
差异集中在**集成度**与**若干"该有但没做"的组件**，共 6 项，按优先级补齐：

| # | 差异项 | 参考架构要求 | 当前状态 | 补齐方式 |
| --- | --- | --- | --- | --- |
| 1 | 临期判定指标 | `新鲜度`、`预计可售天数`、`有风险` | 逻辑在但未落库未上屏 | schema v2 落库 + 接口/页面展示 |
| 2 | 定价约束 | 最低折扣线、每天最多调价 2 次 | **都没有**，已实测出 66.2% 挂价低于成本 | 加约束 + 留痕 + 拦截图 |
| 3 | 敏感性分析 | — | 主对比表未跑 ±30% | 20 种子 × 3 档弹性重跑 |
| 4 | 推送表与归因 | `push_task` + `push_log`（打开率、推送后成交） | 合并为一张表，无归因逻辑 | 拆表 + 3 小时窗口归因 |
| 5 | 定时任务与客流规律 | 每小时临期扫描、每晚重算 `traffic_profile` | 全靠手动查询 | 只读定时扫描 + 星期×小时聚合 |
| 6 | 顾客端 H5 | H5 特价页 | 无（只有群发文案） | 新增 H5 特价页 |

## 1. schema v2（已冻结）

已写入 `src/main/resources/db/schema-h2.sql` 与 `db/schema-mysql.sql`（两文件字段/索引语义一致）。变更点：

### A. `fruit_batch` 新增临期判定指标（对应参考表《临期判定》）

| 字段 | 口径 | 参考架构对应 |
| --- | --- | --- |
| `freshness` | `剩余天数 ÷ 标准保质期`，0~1 越小越不新鲜 | 新鲜度 |
| `estimated_sellable_days` | `剩余库存 ÷ 近 7 天日均销量` | 预计可售天数 |
| `planned_sale_qty` | `min(剩余库存, 日均销量 × 剩余天数)` | 到期前预计销量 |
| `expected_scrap_qty` | `剩余库存 − 预计销量` | 预计报废量 |
| `at_risk` | `预计可售天数 > 剩余天数`，布尔 | 是否有风险 |
| `metrics_updated_at` | 上述指标最近一次计算时间 | — |

**口径要点（答辩会被问）**

- 日均销量窗口取 **近 7 天该单品销量 ÷ 有效营业天数**（无销量日算 0，不剔除，避免把"卖不动"美化成"没数据"）；
  样本不足 3 天时用"该品类同期日均 × 该单品近 3 天占比"兜底，并在 `reason` 里注明是兜底口径。
- `freshness` 与 `at_risk` 是**两个不同维度**：前者说明"离坏还有多久"，后者说明"按现价卖不卖得完"。
  参考架构的示例（香蕉：新鲜度 0.4、预计可售 3.33 天、剩余 2 天 → 有风险）在系统里可复现，见第 3 节验收。
- `days_left` 仍保留（整数天，用于规则分档）；`freshness` 是更细的连续信号，两者并存、用途不同。

### B. 定价约束留痕（对应参考表《定价引擎》第 4 步）

| 字段 | 含义 |
| --- | --- |
| `pricing_suggestion.price_floor_hit` | 建议价被"最低折扣线"拦住（本来想更低但触底） |
| `pricing_suggestion.raw_discount_rate` | 被约束前的原始档位，用于说明"本可以更低" |
| `pricing_suggestion.adjust_seq` | 该批次当天第几次调价（1/2/3…），受每日上限约束 |
| `pricing_suggestion.freshness / estimated_sellable_days / expected_scrap_qty` | 建议生成时的判定指标快照，事后可复核 |
| `pricing_decision.reject_reason` | 店主不接受时的原因枚举（自由文本也兼容） |

新增配置（`application.yml`，带默认值）：

```yaml
app:
  pricing:
    min-discount-rate: 0.60      # 最低折扣线：任何策略都不得低于该价格比（店主可调）
    max-adjust-per-day: 2        # 同一批次每天最多调价次数
```

### C. 推送拆表（对应参考表 `push_task` / `push_log`）

- `push_task`：**计划**——关联单品/批次/建议、`plan_time`（高峰前 30~60 分钟）、选人规则、文案、状态（PLANNED/SENT/CANCELLED）。
- `push_log`：**发送与效果**——每个任务对每个会员一行（群发文案 `member_id` 为空），记录 `opened/opened_at`、`converted/converted_at`、`related_sale_id`、`convert_window_hours`、`skip_reason`。
- **归因口径**：推送发出后 **3 小时内**、该会员购买**同一单品**的销售记录视为转化；`related_sale_id` 指向命中的那条 `sales_record`。
  窗口与"同单品"两个条件都写进 `docs/05` 合规说明的边界里（不做跨品类、不追踪长期行为）。

### D. 新增 `shop_traffic_profile`（对应参考表 `traffic_profile`）

按 **星期 × 小时** 聚合：`avg_order_count`（按样本天数平均，不是按日历天数，避免闭店小时把工作日拉低）、`sample_days`、`is_peak`、`computed_at`。
由"每晚重算"改为**按需重算 + 只读定时任务**（口径见第 2 节），结果落这张表，H5 与工作台都读它。

### E. 其他

- `sales_record.member_id` 新增（归因需要，仅存会员 id，不含手机号）。
- v1 的 `push_message` 表**已删除**，由 `push_task` + `push_log` 取代。

## 2. 定时任务与"无自动执行"的关系（重要口径）

`docs/05` 承诺并已用测试锁定：**系统不得自动改价、自动改批次状态、自动发消息**（`NoAutonomousActionTest`）。
参考架构要求"每小时扫描""每晚重算"。两者不冲突，边界如下：

| 允许（只读/派生计算） | 禁止（业务状态变更） |
| --- | --- |
| 定时扫描临期批次、**计算并写入派生指标**（freshness 等） | 自动修改 `remain_qty` / `status` |
| 定时重算 `shop_traffic_profile` | 自动生成 `pricing_decision` |
| 定时刷新"有风险"清单、写日志 | 自动把 `push_task` 置为 SENT / 自动发 `push_log` |

**判定标准**：定时任务只写"计算出来的字段"和"任务自己的日志"，**不写任何决策结果**；所有业务状态变更必须由显式接口调用触发。
这条边界会同时写进 `docs/05`（合规）与 `docs/01`（技术），并补一条测试：定时任务跑一轮后 `pricing_decision` / `push_log` / `sales_record` 零新增。

### 5.1 敏感性结论（新增，回答参考架构《仿真与评测》第 6 行的担忧）

**口径**：三档 × 6 种子 × 三策略，**与主报告同源**（同一批判定逻辑、同一时间切分、
**同一最低折扣线 0.60**）。命令：`scripts/sensitivity_elasticity.py --seeds 6 --min-discount-rate 0.60`。

| 弹性档 | MODEL−RULE 毛利 | 逐种子胜出 | MODEL−FIXED 毛利 | 损耗率（MODEL−FIXED） |
| --- | --- | --- | --- | --- |
| ×0.7（真实弹性更接近 0） | **+38,731 元** | **6/6** | −13,298 元 | −0.02 pp |
| ×1.0（主报告口径） | **+18,604 元** | **6/6** | −15,099 元 | −0.07 pp |
| ×1.3（水果弹性更大） | **+10,298 元** | **6/6** | −8,885 元 | −0.09 pp |

两条结论对弹性幅值都稳健：**① MODEL 优于经验规则（RULE）在三档下逐种子全胜；
② "降损耗必须付毛利代价"（MODEL−FIXED 为负、损耗率差为负）在三档下都成立。**

> 补充读法：MODEL 对 RULE 的优势随弹性增大而**收窄**（38,731 → 18,604 → 10,298 元）——
> 弹性越大，RULE 那种深折扣越能靠增量销量自救，这与理论一致；但即使在最有利的 ×1.3 档，
> MODEL 仍然逐种子全胜。

### 5.2 口径对齐记录（2026-10-11）

初版报告与敏感性是在**最低折扣线上线之前**生成的（RULE 可一路降到 5 折）。核对发现：
Python 评测跑的是自己那套策略实现，**Java 侧的折扣底线并不影响评测**，所以两者当时确实不同源。
现已把 `--min-discount-rate`（默认 0.60）加进 `evaluate_strategies.py`、`sensitivity_elasticity.py`、
`export_strategy_stats.py` 与 `pricing_rule.py` / `pricing_model.py`，三份产出全部重跑，
与系统侧 `app.pricing.min-discount-rate` 同口径。

| 指标（×1.0） | 约束前 | 约束后（现行） |
| --- | --- | --- |
| FIXED 毛利 / 损耗率 | 68,415 / 13.55% | 68,370 / 13.58% |
| RULE 毛利 / 损耗率 | 49,471 / 4.82% | 49,861 / 4.99% |
| MODEL 毛利 / 损耗率 | 59,244 / 7.61% | 60,194 / 7.84% |
| MODEL 每降 1pp 的毛利代价 | 1,544 元/pp | **1,424 元/pp**（RULE 2,155 元/pp，便宜 34%） |

结论方向完全一致（MODEL 对 RULE 20/20 全胜、对 FIXED 0/20）；约束让三策略的损耗率都略降、
毛利都略升。约束前的对照备份保留在 `release/_evaluation-report.pre-floor.md` 与
`release/_sensitivity.pre-floor.md`。
